## Схема и операции

`assembly/model.js` не импортирует React, DOM или Tauri. Он получает проект и каталог как обычные объекты. Благодаря этому проверки GPIO, питания, модулей, переназначения и удаления тестируются через Node.js.

Канонические физические связи находятся в `assembly.connections`. При создании, переназначении и удалении связи синхронно обновляются производные `gpioAssignments`. GND допускает несколько потребителей; сигнальный GPIO закрепляется за одним контактом. Редактор не поддерживает прямую связь двух контактов платы или произвольную цепь питания.

Неизвестное подключение периферии ограничивает общие GPIO. Ревизия чипа P4 выбирается из документированных вариантов; неподдерживаемое значение блокирует генерацию. Неподтвержденная ревизия платы S3-ETH дает предупреждение. Ошибки параметров или монтажа не мешают сохранять черновик, но видны в нижней панели. Нарушения структуры файла блокируют чтение/запись. Подключение, запрещённое правилами, отклоняется при клике/выборе контакта. Изменение параметров платы может сделать уже существующую связь ошибочной; она сохраняется красной, чтобы пользователь видел проблему.

Добавление компонента фиксирует точную версию общей библиотеки. Удаление убирает связи, положение, GPIO и больше не используемую версию. Смена платы требует подтверждения при наличии связей, затем очищает их и GPIO, сохраняя компоненты и их параметры.

`hardware/resources.js` собирает ресурсы устройств из профиля платы и настроек физического подключения. Одинаковые I2C и LDO разрешено разделять только при совпадающей конфигурации; GPIO и исключительные интерфейсы I2S/DSI/CSI проверяются на конфликты. `firmware/drivers/peripheral-buses.js` создает общие шины и питание один раз.

## Холст

Монтаж и логика используют React Flow как движок холста. SVG-изображения платы и компонентов находятся внутри физических узлов монтажа; координаты контактов берутся из существующего каталога и используются для позиционирования handles. Провода отображаются как edges с сохранёнными ID и без изменения формата проекта. Подключения разрешены между платой и компонентом в любом направлении перетаскивания; электрические ограничения по-прежнему проверяет assembly/model.js. Плата и компоненты перемещаются локально; итоговые координаты и камера передаются в проект после отпускания. Оба холста используют обработку колеса/трекпада React Flow и общие кнопки/клавиши навигации. Первоначальное вписывание при стандартной камере не переписывает проект. Сохранённая нестандартная камера восстанавливается.

Автоматический маршрут обходит подписи контактов и другие компоненты; внутренняя область собственной платы допускает выход провода. Ручное перемещение участка выполняется по одной оси с закрепленными концами. Промежуточные точки сохраняются в `assembly.connections[].route`; сброс удаляет поле и восстанавливает автоматическую прокладку. Геометрия соединений не меняет GPIO или идентификатор прошивки.

Отдельная вкладка логики использует React Flow. Канонические JSON-узлы преобразуются в runtime-узлы, поэтому выбранность, размеры DOM и callbacks не попадают в проект. React Flow загружается отдельным пакетом при открытии вкладки; JSX-редактор не содержит генератора. Монтаж не имитирует выполнение прошивки, LED или активные сигналы.

## Файлы и системный слой

Tauri предоставляет команды `list_projects`, `storage_path`, `save_project`, `delete_project`, `import_project`, `export_project`, `change_project_directory`. По умолчанию данные лежат в системном каталоге приложения, имя файла основано на UUID. Выбор другого каталога сохраняется отдельно в `project-storage.json` внутри `app_config_dir`. Запись выполняется через временный файл в том же каталоге, синхронизацию и атомарную замену.

Смена папки выполняется после завершения очереди записей и сохранения текущего черновика, с паузой автосохранения. Rust выбирает каталог через нативный диалог, проверяет возможность записи, конфликты файлов и копии JSON, затем атомарно записывает настройку пути. Исходные файлы остаются резервной копией; при ошибке настройки новые копии удаляются, уже существующие файлы не изменяются. Записи, чтение списка и смена папки сериализуются одним mutex. Недоступный пользовательский каталог не заменяется каталогом по умолчанию и автоматически не создается. Браузерный предпросмотр сохраняет прежний localStorage.

Результат записи подтверждается до обновления отметки сохранения. Ошибка оставляет правки в форме. `useRef` блокирует повторный запуск файловой операции немедленно. Несохранённые изменения защищаются при переходе, закрытии окна и выходе через меню/⌘Q.

Rust принимает версии формата 1, 2 и 3; JavaScript проверяет полную структуру. Форматы 1/2 преобразуются в памяти без автоматической записи. Browser localStorage по-прежнему использует тот же ключ, чтобы старые записи читались; native/browser-хранилища независимы.

Нет API произвольной записи по пути frontend или выполнения shell-команд. ESP-IDF-команды типизированы и принимают фиксированные параметры; произвольная команда/argv из UI не принимается. Не проверена одновременная запись несколькими экземплярами приложения и устойчивость при отключении питания.

## Граф, история и запись

`logic/model.js` работает с обычным JSON и каталогом, без React/React Flow. Проверяет направление и типы портов, занятые входы, дубликаты и циклы. Привязка GPIO проходит через ID компонента и его физическое назначение. Монтаж и логика используют одну карту точных версий; удаление аппаратного компонента не удаляет версии используемых логических модулей.

История сохраняет снимки узлов/связей; камера сохраняется отдельно и не расходует Undo. Перемещение передаётся в проект одним изменением после отпускания и занимает один шаг Undo; ключ параметра группирует набор текста. История принадлежит Workspace текущего проекта, поэтому не сбрасывается при переключении вкладок.

`useProjects` хранит актуальный черновик для асинхронных операций. Автосохранение по умолчанию включено для всего проекта: обзор, монтаж и логика. Запись откладывается на 10 секунд без дальнейших правок. Режим можно отключить в настройках студии; выбор сохраняется локально между запусками. Ручное сохранение кнопкой или ⌘/Ctrl + S доступно в обоих режимах. Перемещение блоков/компонентов и панорама обновляют локальные координаты холста; итог передаётся в проект один раз после отпускания. Во время перетаскивания и перемещения камеры отложенное сохранение приостановлено. `writeQueue` сериализует записи и не ломает очередь после ошибки. Подтверждение снимка меняет форму только при отсутствии новых правок. Сохранение всегда атомарно для всего проекта. Навигация проверяет выполняющуюся запись, а вопрос о несохранённых данных приостанавливает отложенную запись. Переключение внутренних вкладок и открытие настроек сохраняют черновик и не отменяют ожидающую запись. При ручном режиме они не записывают проект на диск.

## Firmware и ESP-IDF

Генератор сортирует стабильные ID, проверяет точные поддерживаемые версии модулей и зарегистрированные ключи реализаций. Профиль платы определяет ESP32-S3/Xtensa или ESP32-P4/RISC-V, Flash, доступные режимы консоли и настройки ревизии. Положение, имена, камера холста и ручные маршруты не меняют код.

SHA-256 вычисляется над JSON-массивом `[boardId, consoleMode, mainC]`, к которому по порядку добавляются присутствующие `graphicsRuntime`, `networkRuntime`, `boardRevision` и непустой массив `featureRuntimes`. Последний сортируется генератором. Rust независимо проверяет сумму, разрешенные платформы и профили, затем создает собственные CMake/config-файлы из встроенных данных. Native не выполняет переданный frontend CMake или shell. `runtime-profiles.json` задает точные версии управляемых компонентов и настройки DSI, аудио и камеры.

Каталог `<app_cache>/firmware/<fingerprint>-<sdk-root-hash>/` принадлежит CLEX Flow. `idf.py -D IDF_TARGET=<target> build` выполняется установленным Python с проверенным окружением, без shell и изменения SDK submodules. Цель берется из встроенного профиля платы. Для графики и новых периферийных драйверов Component Manager разрешен с фиксированным манифестом и отдельным кэшем сборки; для обычной GPIO-прошивки он выключен. Результат считается успешным после кода выхода 0 и чтения бинарников/flash_args. Изменение схемы, консоли, ревизии, профилей драйверов или SDK делает прежний build неактуальным. Flash проверяет SHA-256 bootloader, partitions, app и flash_args, затем запускает esptool с фиксированными аргументами. Новая сессия требует повторной сборки.

`esp_timer` ставит события в очередь; один FreeRTOS worker выполняет действия по DAG, читает кнопки и применяет debounce. GPIO LED начинает с низкого уровня. Потери очереди явно журналируются. Нет вызовов Serial/долгих действий в таймерном callback. Текст экранируется в UTF-8 octal C-литералы и передаётся как `%s`; суммарные статические текстовые буферы ограничены 64 КиБ.

Операции сериализуются системным сервисом. stdout/stderr читаются в разных потоках; события доступны также через backlog, чтобы не терять начало процесса. Cancel завершает принадлежащую приложению группу процессов на Unix, дерево через taskkill на Windows. Эти Windows/Linux ветки пока не проверены. Serial читает pyserial в отдельном процессе; состояние «Подключён» появляется только после фактического открытия порта. Логи ограничены по длине и количеству, UTF-8 сохраняется между chunks. Монитор только читает и не отправляет команды устройству.

Подробнее об управлении инструментами: [sdk-manager.md](sdk-manager.md).

## Дисплеи

`displays/` содержит независимые от платы и драйвера модель интерфейса, общий редактор и предпросмотр. Данные сохраняются в `project.screens` по ID аппаратного экземпляра. Логический блок ссылается на тот же ID. Каталог отдельно описывает контроллер и модель модуля. `firmware/drivers/` выбирает аппаратную реализацию по платформе и ключу; общая графическая часть создаёт объекты LVGL. Нативная подготовка сборки допускает только закрепленную графическую библиотеку LVGL 9.2.2, драйверные зависимости и встроенные ресурсы шрифтов, без пользовательских команд установки.

Реализованы ST7789/SPI и JD9365/MIPI-DSI с GT9271 через драйвер семейства GT911. Аудио ES8311/I2S воспроизводит тон, OV5647/CSI получает кадры и диагностику. Их задачи передают копии результатов в очередь графа; объекты LVGL обновляются задачей логики. Вывод видеопотока на дисплей пока отсутствует.

## Проверки и границы подтверждения

`npm test` проверяет модели, генерацию, совместимость проектов и маршруты. `cargo test --manifest-path src-tauri/Cargo.toml --locked` проверяет системный слой. После Rust-тестов `npm run test:firmware-parity` сравнивает JavaScript- и Rust-файлы прошивки в 24 конфигурациях S3/P4/Nano без ESP-IDF, сети или устройства. Эта проверка включена в нативный CI macOS/Windows; изменения `src/` и тестов тоже запускают его.

Аппаратная совместимость и ограничения описаны в [README](../README.md#платформы) и руководствах по платам. Компиляция и сравнение файлов не заменяют проверку периферии на устройстве.

Версия в оболочке берётся из `package.json` через `version.js`. Обзор проекта показывает сведения о проекте; каталоги добавления расположены в монтаже и логике. Глобальная библиотека служит просмотром встроенного каталога. Журнал следует за выводом и изменениями высоты, а ручная прокрутка приостанавливает слежение до возврата к концу.

## Arduino AVR

Профиль платы выбирает платформу, цель и версию инструментов. Общие проект, монтаж и типизированный граф сохраняются. `src/firmware/platforms/arduino-avr.js` генерирует Arduino C++ для поддерживаемых модулей, а `src-tauri/src/arduino.rs` обнаруживает инструменты, подготавливает sketch, компилирует, проверяет память ELF и запускает обычную загрузку через AVRDUDE/CLI. Общее управление операциями, отменой, журналом и актуальностью сборки остается в `idf.rs`; существующие имена IPC сохранены для совместимости. Выбор загрузчика включен в fingerprint. `tooling.rs` подготавливает все поддерживаемые семейства последовательно в общей операции; каждый пакет находится в отдельном каталоге.

## ESP-NOW

`src/espnow/model.js` проверяет радио, параметры и подтверждение команд. Peers хранятся как JSON-строка в существующих примитивных параметрах компонента, без смены формата проекта. `EspNowSettings.jsx` предоставляет список полей вместо ручного редактирования JSON. `firmware/drivers/espnow.js` соединяет фиксированный ESP-IDF-драйвер с существующими портами и функциями графа. Колбэк Wi-Fi копирует ограниченный пакет в очередь; `flow_worker` обрабатывает его и вызывает события графа. Отдельного исполнителя логики для ESP-NOW нет. Конфигурация SDK задается существующим профилем `espnow-s3`. Возможности радио объявлены только в соответствующих S3-профилях плат. `gpio-edge.js` и AVR-реализация создают универсальные события цифрового входа после существующего антидребезга.

ESP-NOW представлен четырьмя логическими типами: send, receive, ack и control. Весь набор вместе с аппаратным компонентом clex.hardware.espnow имеет единую версию v2.0.0. Параметры и контакты выбираются существующим каталогом с условиями `when`. Переключение действия через `updateNode` удаляет исчезающие контакты вместе с их связями; разные смыслы событий имеют разные ID. Общие контакты сохраняются. Старые типы блоков не поддерживаются и не преобразуются. Все активные контакты логических блоков отображаются постоянно.

Библиотека логики проверяет наличие совместимого компонента в монтаже до добавления аппаратно-зависимого блока. Проверка использует существующие ограничения модуля и `moduleProblem`; завершенная проводка не требуется. Причина недоступности показана в подсказке. Таймер, счетчик, секундомер и Serial не требуют отдельного компонента; проверка интернета требует сетевой интерфейс. Удаление оборудования отключает добавление зависимых блоков, но не удаляет существующую логику.

Сенсорная кнопка (`clex.hardware.touch-button`, v1.0.0) использует общий цифровой GPIO-вход. Выбранный HIGH/LOW нормализуется при опросе перед существующим фильтром; блоки чтения и изменения получают активное состояние. Механическая кнопка без этого параметра сохраняет прежнюю полярность и подтяжку. Напряжение VCC может задаваться параметром терминала, а OUT проверяется на совместимость с логическим напряжением платы. Подробности: [сенсорная кнопка](touch-button.md).

Выбор платы вынесен в общий `BoardPicker` для создания проекта и «Монтажа». `BoardChoice` показывает только текущую плату; поиск и фильтры работают по существующему каталогу, а список прокручивается внутри диалога. Модель проекта и существующее подтверждение очистки проводов при смене платы не изменены. В списках «Все» аппаратные компоненты и логические блоки упорядочены по тем же категориям, что кнопки фильтров; холст при этом не изменяется.
